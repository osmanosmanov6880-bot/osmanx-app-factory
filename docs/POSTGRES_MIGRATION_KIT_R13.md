# OSMANX APP FACTORY — PostgreSQL Migration Kit (R13 baseline)

**Статус:** реализован инструмент ХОЛОДНОГО переноса и проверки. **Не является переходом рабочего сервера на PostgreSQL.**

Этот пакет создан из последней полной копии исходников, доступной в текущей среде: `OSMANX_APP_FACTORY_R13_SOURCE.zip` (R1.3). Исходники v0.25.0 здесь не доступны. Поэтому **не переименовывайте эту сборку в v0.26.0 и не ставьте её поверх v0.25.0**: это независимый комплект на базе R13 с утилитами, которые предстоит интегрировать в более новую кодовую базу.

## Что работает

1. **Предпроверка:** обнаруживает отсутствующие/чужие базы проектов, повреждения SQLite, нарушения FK, неподдерживаемые триггеры и представления, подмену баз симлинками; проверяет допустимость SQLite-схемы для строгого SQL-транслятора.
2. **Холодный экспорт:** применяет существующий exclusive maintenance-lock, снимки через `node:sqlite.backup`, отдельно создаёт `ox_studio` и одну схему `ox_p_<uuid>` на каждый проект. Формирует PostgreSQL `CREATE TABLE`, PK, FK, уникальные ограничения, обычные индексы, `CHECK`, заполнение таблиц и журнал контрольных хешей. Для каждой схемы — отдельная транзакция, без частичного применения внутри схемы.
3. **Безопасность:** экспорт требует явного флага `--allow-sensitive`; готовые файлы пишутся с правами 0600, папки — 0700, без перезаписи и утечки персональных строк в консоль. Никакие сессии, CSRF-токены и хеши токенов **не экспортируются** (повторный вход обязателен). Парольные хеши пользователей, роли и остальные данные сохраняются.
4. **Проверка результата:** `pg:verify` сверяет хеш каждого SQL-файла с `manifest.json`. `pg:verify-target` через `psql` независимо читает строки целевой PostgreSQL и сверяет количество и SHA-256 всех нормализованных значений с исходной SQLite. Сверка выполняется без записи в целевую БД.
5. **Разделение доступов:** `access.sql` *отдельно* создаёт `NOLOGIN` роли `ox_ro_*` и `ox_rw_*`, выдаёт им разрешения лишь на их схему и отбирает доступ PUBLIC. Он **не применяется автоматически**. Включение этих ролей в учётные записи и проверка пользовательских полномочий — задача будущего PostgreSQL backend.

## Проверка на синтетических данных

```sh
npm run check
npm test
npm run pg:demo -- --out ./my-demo-pg
npm run pg:verify -- --in ./my-demo-pg
```

`pg:demo` генерирует **синтетические**, а не настоящие клиентские записи; создаёт тестовые CRM и сайт и запускает тот же алгоритм экспорта. Данные из `./data` не используются.

## Перенос собственных SQLite данных: только при остановленной фабрике

**Требования:** Node.js 22.16+, доступ к оригинальной папке `data`, PostgreSQL 15+ и утилита `psql` в системе. SQL-экспорт можно сформировать офлайн без установленной PostgreSQL.

```sh
# 1. Остановите фабрику и все отдельные приложения, убедитесь, что нет другого писателя.
npm run pg:plan -- --data ./data

# 2. Держите результат на зашифрованном диске, вне публичных папок и репозитория.
npm run pg:export -- --data ./data --out ./private-migration --allow-sensitive

# 3. Проверьте манифест и SQL до подключения к PostgreSQL.
npm run pg:verify -- --in ./private-migration
```

`pg:plan` не переносит данные и не создаёт SQL; он показывает число таблиц и строк. Миграция **не** инициализирует отсутствующие базы: такой проект нужно сначала открыть штатным сервером, остановить его и повторить предпроверку.

**Только для новой пустой целевой PostgreSQL** настройте подключение стандартными `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER` и защищённым `.pgpass` (не вводите пароли в командной строке). Затем исполните `studio.sql` и `project-*.sql` по одному:

```sh
psql -X -v ON_ERROR_STOP=1 -f ./private-migration/studio.sql
for file in ./private-migration/project-*.sql; do
  psql -X -v ON_ERROR_STOP=1 -f "$file" || exit 1
done
```

**ОБЯЗАТЕЛЬНО:** целевая БД должна оставаться без операций записи во время сверки:

```sh
npm run pg:verify-target -- --in ./private-migration
```

При прохождении сверки **по желанию** примените `access.sql` ролью администратора PostgreSQL с правом `CREATEROLE`:

```sh
psql -X -v ON_ERROR_STOP=1 -f ./private-migration/access.sql
```

`access.sql` выдаёт права **NOLOGIN-ролям**, а не произвольным пользователям. Привязку конкретных учётных записей к ролям нужно реализовать и проверить отдельно. Роли проекта не получают права на схему фабрики или другого проекта. Следует провести ещё проверку RLS/авторизации PostgreSQL-адаптера перед запуском внешнего SaaS.

## Ограничения / release gate

- **Переключение приложения на PostgreSQL НЕ выполнено.** `server.mjs`, `studioDb`, `crmDb`, `siteDb` и автономные ZIP используют `node:sqlite`; никакой строки `DATABASE_URL` у рабочего сервера не появилось. Отсутствуют API адаптер PostgreSQL, фоновые воркеры под PG и подтверждённый промышленный нагрузочный тест.
- **Реальный PostgreSQL недоступен в данной среде**, поэтому целевые SQL-запросы проверены генератором, статическими проверками и тестовым процессом, имитирующим `psql`, но **не были исполнены на настоящем PostgreSQL-сервере**. Чтобы снять ограничение, выполнить перенос тестовых данных в PostgreSQL 15+, потом `pg:verify-target`, проверить проверку ролей, конкурентные транзакции и откат.
- Отдельная транзакция на каждый проект не является общей транзакцией для всех схем. При сбое между файлами нужно очистить уже импортированные тестовые схемы и повторить запуск; не направляйте подготовленный SQL на используемую БД.
- Шифрование артефактов *внутри инструмента* отсутствует; требуется зашифрованное хранилище оператора. Нельзя коммитить SQL-экспорт в Git или отправлять в публичный облачный каталог. В миграции остаются личные данные и парольные хеши.
- `CHECK` поддерживает только ограниченный безопасный набор выражений; при появлении нестандартных `CHECK`, триггеров, view, expression/partial indexes или неизвестных типов миграция **прерывается**, вместо потери ограничения.
- Старые приложения могут хранить пользовательские файлы вне SQLite. Этот модуль переносит **только таблицы SQLite**, без вложений и объектного хранилища. Для v0.25.0 потребуется отдельный проверенный перенос файлов с SHA-256 и метаданными.
- `SHA-256` обеспечивает контроль неизменности экспортированных данных, но не авторство; подписывание и внешняя проверка цепочки доверия не реализованы.
- До подключения PostgreSQL runtime нужен подробный аудит RBAC, tenant isolation, backup/restore, миграций и внешнего security audit.

## Структура и технические компоненты

- `src/migration/pg-kit.mjs` — исследование SQLite, конвертер схем, преобразование строк, вычисление хешей, проверка целевой PostgreSQL и политика ролей.
- `scripts/pg_migration.mjs` — CLI: plan / export / verify / verify-target.
- `scripts/pg_demo.mjs` — локальная генерация синтетического сценария.
- `tests/pg_migration.test.mjs` — автоматические проверки целостности, tenant isolation, сессий, отказов, прав файлов, SQL-хешей и потокового `psql`-верификатора.
- `manifest.json`, `studio.sql`, `project-*.sql`, `access.sql` — результат экспорта. Их **не** следует включать в ZIP исходников с реальными данными.
