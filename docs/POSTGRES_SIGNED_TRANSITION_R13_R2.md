# OSMANX APP FACTORY — PostgreSQL Signed Transition Kit R2

**Статус:** исполняемый инженерный набор на базе R13, **НЕ v0.25.0** и **НЕ production cutover**.

Платформа, интерфейс OBSIDIAN, существующие CRM/сайты и их SQLite-базы **не переключены** на PostgreSQL. Реальный сервер PostgreSQL / утилита `psql` в среде выпуска отсутствуют, поэтому подтверждены проверки Node.js, эмуляция `psql` и синтетический offline-экспорт. Настоящий PostgreSQL 15+ требует отдельной интеграционной проверки перед использованием.

## Крупные блоки реализации

### 1. Привязка миграции к доверенному подписанту (Ed25519)

- `src/migration/pg-trust.mjs` — создание пары ключей, detached-подпись *точных байтов* `manifest.json`, проверка строго **внешнего доверенного публичного ключа**.
- SHA-256 всех SQL-файлов и ACL привязаны к подписанному манифесту.
- `pg:apply` и `pg:apply-acl` **отказываются** работать без `--trusted-public-key`. `pg:verify` остаётся удобным автономным контролем целостности без утверждения авторства.
- Закрытый ключ создаётся **без парольного шифрования внутри файла**, с правами `0600` на UNIX. Храните его отдельно на зашифрованном носителе, вне репозитория/ZIP/серверов PostgreSQL. При утечке считайте все подписанные пакеты скомпрометированными.

### 2. Потоковый импорт, защита от подмены после проверки

- `src/migration/pg-operations.mjs` считывает SQL через единый дескриптор файла, с `O_NOFOLLOW` там, где ОС поддерживает, и пересчитывает SHA-256 **во время передачи**.
- Если содержимое SQL изменилось после предварительной проверки, процесс не закрывает входной поток `psql`, уничтожает дочернее соединение и не заявляет об успешной транзакции.
- Запрещены управляющие команды клиента `psql` с обратной косой чертой. SQL нескольких проектов подаётся в **одну** целевую транзакцию `--single-transaction`.
- Проверка большого SQL-файла по SHA-256 использует поток, без `readFile` всего экспорта в память.
- Предсуществующий файл квитанции остановит операцию **до** любых изменений целевой БД.

### 3. Роли организаций, ACL и отдельное подтверждение

- `pg:apply-acl` подписанно применяет только `access.sql` в транзакции и только при `--confirm-tenant-acl`.
- Перед активацией проверяет наличие всех перенесённых схем и отсутствие пересечения с уже существующими глобальными именами ролей.
- `pg:verify-acl` проверяет отсутствие `PUBLIC`-доступа, чужих GRANT, чужих table-level SELECT, `CREATE` в собственной схеме, наследования других ролей, привилегированных атрибутов, и корректность read-only/read-write разрешений.
- **PostgreSQL роли глобальны для кластера.** На общем сервере даже тестовая активация ACL оставит роли кластера; удаляйте их только вручную после анализа и с отдельным подтверждением DBA. Рекомендуется изолированный PostgreSQL-кластер для теста.

### 4. Асинхронный контракт PostgreSQL доступа и объективный release gate

- `src/migration/pg-tenant-adapter.mjs` предоставляет `TenantPgAdapter`: обязательная *серверная* функция авторизации до открытия соединения, роль проекта `ox_ro_*`/`ox_rw_*`, `SET LOCAL ROLE`, `SET LOCAL search_path`, `BEGIN READ ONLY` для чтения, параметризованные запросы, откат и выброс сломанного соединения из пула.
- Интерфейс принимает **внешний** совместимый `pool` (например `pg.Pool`); пакет `pg` не входит в офлайн-сборку и соединения реального приложения к этому адаптеру пока не направляются.
- `pg:assess` сверяет подписанный манифест, SHA-256 из согласованного снимка PostgreSQL и разграничение прав. Он всегда возвращает `postgresqlRuntimeReady:false` и `productionCutoverApproved:false`.

## Безопасная последовательность на синтетическом наборе

```sh
npm run check
npm test
npm run pg:demo -- --out ./synthetic-pg-kit
npm run pg:verify -- --in ./synthetic-pg-kit

# Отдельное защищённое хранилище. Никогда не включать private.pem в ZIP проекта.
npm run pg:keygen -- --out ../private-signing-identity
npm run pg:sign -- --in ./synthetic-pg-kit --key ../private-signing-identity/private.pem
npm run pg:verify-signature -- --in ./synthetic-pg-kit --trusted-public-key ../private-signing-identity/public.pem
```

Проверка **на настоящем PostgreSQL** возможна только с установленным `psql` и конфигурацией `PGHOST`, `PGDATABASE`, `PGUSER`, `.pgpass`. Для удалённого PostgreSQL требуется `PGSSLMODE=verify-full` и корректная цепочка CA.

```sh
# На заранее созданной новой пустой базе PostgreSQL 15+, без клиентских данных:
npm run pg:preflight -- --in ./synthetic-pg-kit
npm run pg:apply -- --in ./synthetic-pg-kit --trusted-public-key ../private-signing-identity/public.pem --confirm-atomic-import
npm run pg:verify-snapshot -- --in ./synthetic-pg-kit

# Только в выделенном тестовом кластере и с полномочием CREATEROLE:
npm run pg:apply-acl -- --in ./synthetic-pg-kit --trusted-public-key ../private-signing-identity/public.pem --confirm-tenant-acl
npm run pg:assess -- --in ./synthetic-pg-kit --trusted-public-key ../private-signing-identity/public.pem
```

Альтернативный автономный тест со **синтетическими данными** (без ACL, без удаления БД):

```sh
# PGDATABASE должен иметь имя вида ox_test_factory_001 и быть пустым.
npm run pg:live-e2e -- --confirm-test-database
```

## Для настоящих клиентских данных

1. **Сначала получить реальный ZIP v0.25.0.** Этот R13-комплект не устанавливать поверх неё и не использовать вместо её схемы.
2. Проверить новую миграцию на точной копии v0.25.0 с изолированным PostgreSQL 15+.
3. Сделать отдельные резервные копии каждой SQLite и пользовательских вложений; остановить все процессы.
4. Экспортировать только в приватную папку: `npm run pg:export -- --data ./data --out /encrypted/pg --allow-sensitive`.
5. Проверить, подписать, повторно проверить подпись, выполнить `preflight` и только затем импорт с подтверждением. `access.sql` применять отдельно.
6. Проверить сценарии прав обычного пользователя в настоящем HTTP API, реальные блокировки/гонки, восстановление и миграции схем. Только после этого рассматривать смену runtime и публикацию.

## Границы проверки

| Компонент | Подтверждение |
| --- | --- |
| Проект R13 и старые функции | Полная локальная регрессия Node.js |
| Подпись/подмена/разные ключи | Автоматические тесты Ed25519 |
| Потоковый импорт и отказ после модификации SQL | Тесты с mock-psql |
| Применение ACL и аудит разделения | Тесты с mock-psql |
| Асинхронный адаптер доступа | Тесты с искусственным пулом |
| Реальные команды PostgreSQL 15+ | **Не проверено** — необходим настоящий сервер |
| Работа приложения с PostgreSQL вместо SQLite | **Не реализовано** |
| Встроенный PostgreSQL драйвер `pg` | **Не установлен, не включён** |
| Конкретный v0.25.0 | **Исходники недоступны** |
| Платежи/публикация | **Не затрагивались** |

**Нельзя воспринимать только прохождение mock-psql тестов как production acceptance.** Для применения в реальном бизнесе необходимы внешние аудиты безопасности/персональных данных и реальный сквозной PostgreSQL + HTTP тест.
