# OSMANX APP FACTORY — R3.0 Preview: подписанные выпуски

**Дата:** 5 ноября 2026. **Основа:** независимая инженерная ветка R1.3 с изменениями R2.4–R3.0; исходная R2.3 не найдена, интеграция и совместимость с ней НЕ подтверждены. В `package.json` оставлена `1.3.0`, так как это версия базового движка, а не номер инженерного Preview. OBSIDIAN сохранён.

## Зачем это нужно

В R2.9 проверялся SHA-256 каждого файла в пакете, но злоумышленник мог заменить файлы и пересчитать хеши. R3.0 добавляет **отдельную цифровую подпись Ed25519**, проверяемую по публичному ключу, который администратор заранее и независимо устанавливает на VPS. Подпись позволяет обнаружить выпуск, который был изменён или создан не тем, кому принадлежит закрытый ключ. Она **не** подтверждает отсутствие ошибок в самом коде.

### Что добавлено в код

- `scripts/release_sign.mjs`: генерация пары ключей Ed25519, подпись ZIP, проверка подписи.
- `templates/deploy/signature.mjs`: проверка подписи и полного перечня файлов. В клиентский пакет входит только этот код проверки, **не закрытый ключ**.
- `templates/deploy/upgrade.mjs`: `plan` и `apply` до остановки контейнеров проверяют целостность и Ed25519, когда ключ закреплён на VPS или передан через `--trust-key`.
- Состояние операции фиксирует факт криптографической проверки и отпечаток доверенного ключа, не включая персональные данные.
- Созданы `scripts/r30_docker_e2e.mjs` и workflow `.github/workflows/r30-signed-release.yml` для реального изолированного Docker-теста. Скрипт написан, но в этой среде Docker недоступен, поэтому фактический Docker-прогон **не утверждается**.
- Для первичной установки и R2.9 без настроенного ключа оставлена явно помеченная совместимость с неподписанными пакетами. **После создания каталога доверия режим становится строгим:** отсутствие публичного ключа, неверная подпись или отсутствие подписи — отказ, без Docker-действий.

## 1. Один раз: создать ключ на доверенном компьютере

Работая в исходной папке фабрики с Node.js 22.16+, создайте ключи **вне исходников проекта**:

```bash
node scripts/release_sign.mjs keygen --private=/secure/osmanx-release-private.pem --public=/secure/osmanx-release-public.pem
```

В Windows укажите собственные существующие защищённые каталоги и кавычки вокруг путей при необходимости. Закрытый ключ **не копировать** на VPS, в браузер, GitHub, архивы клиента, резервные копии CMS или Docker. Скопируйте публичный ключ на VPS по доверенному каналу, сверив отпечаток или содержимое вне канала доставки.

## 2. Скачать выпуск из фабрики и подписать ZIP

Сначала создайте сохранённый выпуск в разделе «Выпуски», затем в мастере публикации выберите именно эту версию с новым номером `sequence`, укажите тот же домен и скачайте ZIP. Фабрика экспортирует комплект **неподписанным**, не получая доступ к закрытому ключу. Подпишите архив **локально**:

```bash
node scripts/release_sign.mjs sign /safe/exported.zip --private=/secure/osmanx-release-private.pem --out=/safe/signed-release.zip
node scripts/release_sign.mjs verify /safe/signed-release.zip --public=/secure/osmanx-release-public.pem
```

Команда откажется перезаписывать существующий ZIP и откажется использовать закрытый ключ с разрешениями для группы/остальных на Unix. ZIP содержит самостоятельную запись `deploy/release-signature.json`, которая подписывает оба манифеста, а манифесты — все исходные файлы. Изменение даже одного файла, его хеша или метаданных после подписи нарушает проверку.

## 3. Закрепить публичный ключ на VPS

В папке уже установленного клиента (пример `/srv/osmanx/client`):

```bash
cd /srv/osmanx/client
mkdir -m 700 .osmanx-trust
# Скопируйте ПУБЛИЧНЫЙ ключ в .osmanx-trust/release-public.pem
chmod 700 .osmanx-trust
chmod 644 .osmanx-trust/release-public.pem
```

Закреплённый ключ должен находиться **вне управляемого перечня файлов релиза**; каталог `.osmanx-trust` исключён из Docker-сборки и Git и не перезаписывается обновлением. Файл и каталог не должны быть доступны для записи посторонним пользователям. Если публичный ключ отсутствует внутри существующего `.osmanx-trust`, система прекращает операцию, а не незаметно возвращается в неподписанный режим.

## 4. План и применение обновления

Используйте обновляющий скрипт R3.0 из заранее проверенного источника. Старый скрипт R2.9 не знает о проверке Ed25519, поэтому для **первого обновления** запускайте скрипт из отдельно распакованного R3.0 комплекта и указывайте установленную папку клиента.

```bash
node /safe/r30-kit/deploy/upgrade.mjs plan /safe/signed-release.zip --installed=/srv/osmanx/client --require-signature
node /safe/r30-kit/deploy/upgrade.mjs apply /safe/signed-release.zip --installed=/srv/osmanx/client --require-signature --confirm
```

Для следующих обновлений после R3.0 внутри установленного пакета:

```bash
node deploy/upgrade.mjs plan /safe/signed-release.zip --require-signature
node deploy/upgrade.mjs apply /safe/signed-release.zip --require-signature --confirm
node deploy/upgrade.mjs status
```

Чтобы использовать внешний публичный ключ без копирования в `.osmanx-trust`, можно передать `--trust-key=/secure/public.pem` вместе с `--require-signature`. Оба пути требуют ручного закрепления доверенного ключа.

**Важное ограничение:** подпись защищает только пакет при использовании проверенного скрипта. Если на VPS злоумышленник может менять исполняемый код `upgrade.mjs` или заменять доверенный ключ, одной подписи ZIP недостаточно. Нужны ограниченные права администратора, защита сервера, журналирование и отдельная проверка доверенной среды.

## 5. Проверки и действительные ограничения

- Локальная регрессия Node.js включает проверку двух типов приложений, подмену файлов и манифестов, неверный ключ, запрет неподписанного ZIP после закрепления ключа, режим `--require-signature`, подлинное обновление локальных файлов и восстановление SQLite с тестовым адаптером Docker.
- Проверки Chromium используют тестовый API, а не браузерное взаимодействие с публичным сервером.
- Реальный Docker E2E подготовлен для **новой временной CRM**, с новой парой ключей в памяти, отсутствием опубликованных портов и специально вызванным сбоем после подписанного обновления. На Linux/CI:

```bash
docker pull node:22-bookworm-slim
npm run docker:e2e:r30
```

**Здесь Docker Engine отсутствует.** Реальное выполнение Docker-сценария, получение сертификатов Caddy, внешний HTTPS, сетевые угрозы, многопользовательская нагрузка и формальный аудит безопасности не подтверждены. Для промышленного SaaS они обязательны.
