# OSMANX DATA STUDIO · R0.3

## Purpose

Replace repeated manual creation of tables, forms, filters, permission guards and CRUD code. Studio stores only the declarative schema and page configuration; CRM keeps real records in its own SQLite database. Exported CRM can run separately.

## Schema contract

```json
{
  "slug":"orders",
  "title":"Заказы",
  "description":"Закупки ресторана",
  "access":{"read":["admin","manager","staff"],"write":["admin","manager"]},
  "fields":[
    {"key":"title","label":"Название","type":"text","required":true},
    {"key":"supplier","label":"Поставщик","type":"reference","target":"suppliers","required":true},
    {"key":"status","label":"Статус","type":"select","options":["Новая","Получено"],"required":true},
    {"key":"quantity","label":"Количество","type":"integer","required":false}
  ]
}
```

The `id`, `revision`, timestamps and `project_id` are generated by Studio. Entity/column identifiers must match strict ASCII regex and cannot equal reserved columns. Identifiers are quoted and never taken from URL without matching the stored server-side allowlist.

## SQLite generation

Tables use physical columns, **not one arbitrary JSON blob**. A validated schema `orders` generates `custom_orders` with `id`, `version`, `created_at`, `updated_at`, `archived_at`, `created_by` and typed data columns. `reference` generates a foreign key to an existing custom table; indexes are created for reference columns. The synchronizer creates base tables before adding reference fields, making self-references and cross-table references possible.

`custom_entity_schema` in the CRM DB records the previous schema contract; on updates, normalization rejects destructive changes. Additive column migrations are wrapped in an IMMEDIATE SQLite transaction. A config signature cache avoids repeat migrations on every request. Studio and CRM databases remain independent.

### Migration policy

**Allowed:** add an optional field, rename its display label, add select options to the end, change entity title/description/role access. **Rejected:** deletion, rename of database identifier, change of field type, change of required flag, change of reference target, removal or reordering of old select options. Old row values are retained after `ALTER TABLE ... ADD COLUMN`.

Schema changes are applied lazily on the next request or startup, not pushed to already distributed ZIP archives. Studio does not inspect or copy the live CRM rows.

## Access and data guarantees

- Factory owner controls schema and pages; CRM user roles control records.
- Each CRM DB is isolated by project UUID.
- Every record API requires a valid session and, for writes, CSRF token plus entity `access.write`.
- Staff may read without writing where the schema says so. Admin always has both permissions.
- Validator rejects unknown columns, malicious identifiers, invalid integers/dates/options and broken references.
- Version (`version`) protects updates and archival against stale edits.
- Pagination defaults to 25 (maximum 100), with offset and capped search over text/select fields. Lists exclude archived rows.
- Archive is soft delete. Linked rows may continue referencing an archived parent; cross-table cascading deletion is intentionally disabled.
- Audit trail records create/update/archive with actor and entity name, not customer payloads.
- No code execution, user-defined SQL, dynamic untrusted endpoint or HTML rendering of text values.

## Generated UI and pages

- CRM navigation auto-adds every visible custom table.
- Each entity generates a list with search, pagination, create/edit form, reference selectors and soft archive button.
- Page Builder permits `custom:<slug>` sources in `form` and `table` blocks; the form must include every required field.
- Button Builder supports `create:custom:<slug>` and `navigate:custom:<slug>`.
- A published page reads real CRM records through secured JSON routes. Config-only Studio previews contain no customer data.

## Limits / not implemented

12 entities per project, 24 columns per entity, max 30 select options, max 100 reference options shown in one dropdown. No CSV import, bulk edits, field deletion/data-type change, filtered relationships, calculated fields, 1:n editor, join visualizations, transactions across multiple user-defined records, background jobs, versioned multi-environment deployments, cloud backups, automatic propagated updates to exported applications or fully pixel-perfect UI designer.

For production security, lifecycle, migration and backup gaps see SECURITY.md and PROJECT_STATUS.md.
