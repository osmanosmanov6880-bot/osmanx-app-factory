# OSMANX APP FACTORY — защищённый атомарный импорт PostgreSQL (R13 kit, следующая итерация)

**Статус:** код инструментария и автоматические тесты готовы. **На реальном PostgreSQL в текущей среде НЕ запускалось**, поэтому не выдавайте это за готовую миграцию production. Исходная база R13, не v0.25.0.

## Что теперь реализовано

### Блок 1. Предварительная проверка целевой базы

`pg:preflight` через `psql` проверяет версию PostgreSQL **15+**, разрешение `CREATE` у пользователя подключения, отсутствие целевых схем и неизменность локальных SQL-файлов по SHA-256. Все идентификаторы целевых схем формируются из идентификаторов проектов в проверенном манифесте. Проверка ничего не меняет.

### Блок 2. Один атомарный импорт

`pg:apply` требует `--confirm-atomic-import`. Из доверенного комплекта, прошедшего проверку SHA-256, файлы подаются в `psql` **потоком**, без второго незащищённого SQL-дубликата. Исходные `BEGIN`/`COMMIT` каждой схемы снимаются, а `psql --single-transaction` оборачивает все схемы в **одну транзакцию**. Внутри неё проверяется отсутствие целевых схем **ещё раз**, под PostgreSQL advisory transaction lock, чтобы устранить гонку между `preflight` и импортом.

Если SQL-ошибка происходит внутри этой транзакции, PostgreSQL должен откатить её. При внезапном разрыве соединения нельзя на 100% знать, видел ли клиент результат COMMIT: до повтора оператор обязан проверить, что на самом деле находится в целевой базе. Инструмент не стирает существующие схемы и не выполняет повторный импорт поверх них. Он не выводит SQL ошибки с пользовательскими строками в обычный журнал.

### Блок 3. Сверка из согласованного снимка

`pg:verify-snapshot` использует **одно** соединение с `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`. Порядок строк задаёт исходный PK. Для каждой таблицы сравниваются количество строк и SHA-256 нормализованных значений. Это защищает от ложного несовпадения, когда между отдельными запросами другие процессы изменяют целевую БД. Проверка не записывает данные.

Автоматический `pg:apply` запускает эту проверку после успешного коммита. Если импорт уже закоммичен, а сверка не прошла, состояние обозначается **`imported-unverified`**; автоматического отката после коммита **нет**. Нельзя переключать приложение или очищать схему до анализа.

### Блок 4. Проверка разграничения прав

`pg:verify-acl` запускается только после **ручного** применения созданного ранее `access.sql`. Проверяет для каждой пары `ox_ro_*`/`ox_rw_*`: роль `NOLOGIN`, отсутствие SUPERUSER/CREATEROLE/BYPASSRLS, наличие своего USAGE, SELECT, нужных DML прав, отсутствие прав на схемы других проектов и неожиданного наследования членства. При малейшем несоответствии — ошибка. Никакие роли или права не создаются автоматически.

### Блок 5. Воспроизводимое испытание на реальном сервере

`pg:live-e2e` строит **полностью синтетические** SQLite CRM и сайт, экспортирует их, проверяет пустую тестовую базу PostgreSQL, импортирует атомарно и подтверждает хеши. Ни одну запись реальных клиентов скрипт не открывает. Запускается **только** при `PGDATABASE=ox_test_*` и явном `--confirm-test-database`. Скрипт не создаёт и не удаляет базу PostgreSQL. Схемы остаются для ручной инспекции; ACL скрипт автоматически не применяет.

## Команды для оператора

### A. Без подключения к серверу

```sh
npm run check
npm test
npm run pg:demo -- --out ./synthetic-pg-kit
npm run pg:verify -- --in ./synthetic-pg-kit
```

### B. Своё тестовое окружение PostgreSQL

На отдельном PostgreSQL создайте **пустую** тестовую базу с именем вроде `ox_test_factory_001`, настройте `.pgpass` и `PGHOST`, `PGDATABASE`, `PGUSER`.

Если сервер удалённый, требуется **`PGSSLMODE=verify-full`** и доверенный сертификат сервера. Не используйте `sslmode=prefer` для передачи клиентских данных; параметры TLS должны соответствовать вашей PKI. Не задавайте пароль прямо в аргументах командной строки.

```sh
# Полностью синтетический тест; PGDATABASE уже указывает на ox_test_factory_001
npm run pg:live-e2e -- --confirm-test-database
```

Это **не было выполнено здесь**, потому что в среде отсутствует доступный сервер `postgres`/`psql`. Для повторного теста нужна другая новая пустая база или ручная очистка тестового окружения DBA; скрипт удалять схемы не будет.

### C. Настоящая миграция (не выполнять на production до полного acceptance)

1. Получите точные исходники нужной версии приложения. Код в этом ZIP — **R13**, а не v0.25.0.
2. Остановите фабрику и автономные приложения. Создайте отдельные офлайн-резервные копии SQLite и пользовательских файлов.
3. `npm run pg:plan -- --data ./data`.
4. `npm run pg:export -- --data ./data --out /encrypted/private-pg --allow-sensitive`.
5. `npm run pg:verify -- --in /encrypted/private-pg`.
6. В новой **пустой** тестовой БД PostgreSQL: `npm run pg:preflight -- --in /encrypted/private-pg`.
7. С явным подтверждением: `npm run pg:apply -- --in /encrypted/private-pg --confirm-atomic-import --receipt /encrypted/private-import-receipt.json`.
8. Дополнительно проверьте: `npm run pg:verify-snapshot -- --in /encrypted/private-pg`.
9. По отдельному решению DBA примените `access.sql` с правами `CREATEROLE`, затем `npm run pg:verify-acl -- --in /encrypted/private-pg`.

**Категорически нельзя:** запускать `pg:apply` без изолированного бэкапа, вводить production-пароль в терминальные аргументы, коммитить SQL с персональными данными в GitHub, запускать тестовый скрипт в production или переключать production runtime по результату одного SQL-импорта.

### Отчёты состояний

- `imported-verified` — транзакция завершилась и хеши таблиц совпали; это ещё **не** подтверждение готовности приложения к работе с PostgreSQL.
- `imported-unverified` — транзакция применена, но проверка целевых данных не завершилась успешно; требуются анализ и повторная проверка без очистки схем.
- `failed-or-uncertain` — клиент не получил доказательство коммита; проверьте целевую БД. После обычной SQL-ошибки транзакция откатывается, но сетевые разрывы требуют отдельного подтверждения.
