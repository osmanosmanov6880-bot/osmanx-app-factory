# OSMANX APP FACTORY R3.3 — параллельная нагрузка и аварийное восстановление

**Статус:** инженерная Preview-сборка на базе R1.3 с последовательными улучшениями R2.4–R3.3. Это не интеграция с отдельным архивом оригинальной R2.3: он недоступен. Дизайн OBSIDIAN не переработан.

## 1. Управляемое завершение HTTP и защита операций

Добавлен общий модуль `src/common/request-drain.mjs`, используемый **обоими** экспортируемыми приложениями (`templates/standalone/run.mjs` и `site-run.mjs`). При SIGTERM/SIGINT новые запросы не допускаются, ранее принятые запросы завершают обработку, после чего закрывается SQLite и снимается блокировка сервера. Если запрос завис, ограничение 75 секунд **не разрешает** преждевременно закрывать рабочую SQLite.

В Compose добавлены `stop_grace_period: 90s` для приложения и `30s` для шлюза. Операторский обновитель сначала останавливает шлюз Caddy, затем приложение с 90-секундным ожиданием. Это **обновление с простоем**, не zero-downtime. Истёкший deadline Docker всё ещё может привести к принудительному завершению процесса, поэтому нужны резервные копии.

## 2. Надёжный журнал и блокировка обновления

`templates/deploy/upgrade.mjs` усилил проверки ID/UUID, имён Compose, списка управляемых файлов, фаз обновления, SHA-256 архива, прав доступа к журналу. При записи активного журнала выполняются синхронизация файла и каталога с диском (POSIX). Журнал не является криптографически подписанным: для подлинности самого релиза используется закреплённый публичный Ed25519-ключ из R3.0/R3.2.

Ранее реальный SIGKILL оставлял каталог блокировки, из-за чего восстановление отказывалось запускаться. В R3.3 `recover --confirm` и `resume --confirm` умеют снять **только подтверждённо устаревшую** блокировку с валидной записью о завершившемся PID. Блокировка активного процесса, неподписанная/непроверяемая запись или опасные пути никогда не захватываются автоматически. Обычная команда `apply` не перехватывает чужую блокировку.

## 3. Параллельная нагрузка настоящих клиентских приложений

`node scripts/r33_load_acceptance.mjs` экспортирует отдельные CRM и сайт с фиктивными данными, поднимает два реальных локальных HTTP-сервера и SQLite, выполняет 36 одновременных созданий клиента, шесть отправок заявки на сайте, по 40 запросов `GET /api/health` для каждого. Затем посылает SIGTERM, ждёт завершения и **после остановки** сверяет число записей и `PRAGMA integrity_check`. Никакой публичный домен не вызывается. Это проверка небольшого локального сценария, а не нагрузочная сертификация высоконагруженного SaaS.

## 4. Аварийное SIGKILL и воспроизводимая приёмка

`node scripts/r33_crash_acceptance.mjs` запускает новый процесс обновления и принудительно убивает его SIGKILL в двух точках — сразу после остановки и после установки новых файлов перед загрузкой. Каждый сценарий выполняется для CRM и сайта. В **другом** процессе операторский `recover --confirm` открывает сохранённый журнал, восстанавливает код, при необходимости SQLite и проверяет canary. Четыре сценария проходят на реальных локальных файлах/SQLite, но **без Docker**.

`node scripts/r33_release_acceptance.mjs --out=/secure/path/r33.json` объединяет предыдущий тест подписанного выпуска R3.2 с локальной нагрузкой и аварийным восстановлением. В отчёт не включаются клиентские записи, пароли, токены и закрытые ключи. `sha256` — контроль целостности отчёта, а не цифровая подпись независимого аудитора.

Workflow `.github/workflows/r33-resilience-acceptance.yml` запускает на GitHub-hosted Ubuntu отдельные офлайн-проверки и Docker-стадию с синтетическими томами. **Факт выполнения GitHub Actions здесь не подтверждён.** На локальном исполнителе Docker Engine отсутствует.

## Как проверить

Node.js 22.16+:

```bash
npm run check
npm test
npm run load:r33
npm run crash:r33
npm run acceptance:r33 -- --out=/private/r33-acceptance.json
```

Для настоящего Docker CI нужен Linux runner с Docker Engine и Docker Compose. Предусмотрен изолированный сценарий с временными томами и фиктивными данными. Не запускайте испытания аварийного восстановления на базе настоящего клиента.

## Степень готовности и ограничения

- Проверены реальные локальные HTTP/SQLite и аварийное завершение отдельного процесса, **не Docker на VPS**.
- Локальные дампы не заменяют независимые зашифрованные офсайт-бэкапы и восстановление с потерянного VPS.
- `SIGKILL` на локальном сервере не эквивалентен отказу питания, накопителя или контейнерного оркестратора.
- Внешний HTTPS, нагрузка с реальными пользователями, аудит безопасности, публичный деплой, полный живой браузерный E2E и интеграция оригинальной R2.3 не подтверждены.
- Внешние платёжные системы и нативные мобильные приложения здесь не созданы.

**Приоритет после R3.3:** запуск CI в GitHub с реальным Docker и согласованный тест на изолированном VPS, затем автоматизированный retention/backup SLO и отчёт о доступности.
