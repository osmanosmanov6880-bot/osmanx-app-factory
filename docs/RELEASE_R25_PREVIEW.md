# OSMANX APP FACTORY — R2.5 PREVIEW / Release Safety

**База исходников:** проверенный архив R1.3 плюс инженерный backport R2.4. Оригинальный R2.3 отсутствует. Это **не** интегрированный R2.5 от официальной ветки R2.3. Версия платформы в package.json осталась **1.3.0**. Тёмный дизайн OBSIDIAN не заменялся.

## Что действительно реализовано

1. **Постоянная идентичность Docker Compose** (`name: osmanx_<projectId>`): тома данных, сертификатов и настроек прокси именуются по UUID клиентского проекта, а не по имени папки. Уменьшает вероятность ошибочного подключения пустого тома при развёртывании следующего комплекта в другом каталоге.
2. **Отдельный сервис обслуживания** с профилем `maintenance`. Контейнер без сети и без лишних прав, Node.js работает от непривилегированного пользователя. База и резервные копии подключаются как отдельные том и каталог; сервер приложения должен быть остановлен.
3. **`deploy/maintenance.mjs`** — команды `backup`, `verify BACKUP_ID`, `restore BACKUP_ID --confirm`. SQLite backup API, `PRAGMA integrity_check`, `foreign_key_check`, SHA-256, проверка project ID, невозможность подменить файл символической ссылкой, отказ при серверных блокировках/WAL, обязательная страховочная копия перед перезаписью БД. Восстановление требует явного подтверждения.
4. **`deploy/verify-live.mjs --live`** — отдельный опциональный внешний HTTPS GET на `/api/health` (не из фабрики), проверка валидности сертификата, HTTP 200 и JSON с `ok=true`. IP берётся из публичной A-записи и закрепляется в HTTPS-запросе, редиректы и частные сети отклоняются. Платёжные транзакции и действия клиентов не проверяются.
5. Расширенные инструкции для администратора, компактный раздел резервирования в мастере OBSIDIAN. Два хешированных манифеста: `manifest.json` старого standalone-контракта и `deploy/manifest.json` версии 2.

## Важное предупреждение при обновлении

**Старые R2.4 deployment ZIP используют зависящие от имени папки Docker volumes.** Их нельзя просто заменить новыми R2.5 файлами с постоянным `name`: приложение увидит новые пустые тома. Перед миграцией требуется составить карту текущих томов, остановить приложение, сделать проверенную резервную копию и **вручную перенести данные** на новые тома. Автоматической миграции R2.4 -> R2.5 в этом релизе нет. Это ограничение намеренное — скрытая миграция персональных данных опаснее ручной.

## На новом VPS (первичная установка)

Требуются: публичный домен с DNS A, VPS Linux, Docker Engine с `docker compose`, открытые TCP 80/443; для HTTP/3 дополнительно UDP 443. Node.js 22.16+ нужен для локальных операций с архивом и генерации начального токена.

После распаковки **на новом чистом сервере**, в каталоге клиента:

```bash
node deploy/verify.mjs
node deploy/prepare.mjs
node deploy/preflight.mjs
mkdir -p backups
sudo chown 1000:1000 backups
chmod 700 backups
docker compose config --quiet
docker compose up -d --build
docker compose ps
node deploy/verify-live.mjs --live
```

`verify-live` действительно обращается к публичному HTTPS-адресу, но **только** по явному запуску. Команда проверяет лишь IPv4 A-записи: для IPv6-only развёртывания используется отдельная ручная проверка. DNS-проксирование и сторонний CDN могут изменить маршрут проверки.

## Бэкап и восстановление

Команды требуют остановить приложение. На время обслуживания Caddy может показывать 502 — предупредите пользователей и выберите окно обслуживания.

```bash
docker compose stop app
docker compose --profile maintenance run --rm --no-deps maintenance backup
docker compose --profile maintenance run --rm --no-deps maintenance verify BACKUP_ID
docker compose up -d app
```

**Для восстановления:** остановите приложение, убедитесь, что нет активных записей, выберите проверенный `BACKUP_ID` из каталога `backups`.

```bash
docker compose stop app
docker compose --profile maintenance run --rm --no-deps maintenance restore BACKUP_ID --confirm
docker compose up -d app
node deploy/verify-live.mjs --live
```

При аварийном останове может остаться `server.lock` или SQLite WAL. Система **намеренно не удаляет их автоматически**; нужно отдельно проанализировать последствия сбоя. Не удаляйте lock работающего сервера. Резервные копии содержат персональные данные и **не шифруются этим модулем**: используйте отдельный зашифрованный offsite backup, ограничения доступа и проверку восстановления на стенде. TLS-данные Caddy также нужно резервировать отдельно.

## Испытания

- `npm run check` — проверка синтаксиса.
- `npm test` — **40/40 автоматических тестов** (34 предыдущих + 6 новых). Новый тест проверяет копии и восстановление CRM/сайта, атакующие/сбойные случаи, сохранение идентичности томов и безопасную публичную HTTPS-проверку с **имитацией сетевого ответа**.
- `python3 tests/ui_r25_deploy_static.py` — адаптивный Chromium с **mock API**, 1440px и 390px.
- Живые Node.js HTTP-тесты из предыдущего релиза продолжают проходить, но **живой браузерный E2E не заявлен**.

**Не проверено:** запуск Docker Compose на реальном VPS, публичный DNS/сертификат с реальным доменом, полная безопасность контейнерного хостинга, долгосрочное восстановление после катастрофы. Это не готовая production SaaS-платформа.
