# OSMANX APP FACTORY — R2.7, наследуемые тома Docker

**Выпуск:** 5 ноября 2026 года. **Фактическая база кода:** R1.3 с перенесёнными инженерными изменениями R2.4–R2.7. Архив исходной R2.3 в этой рабочей среде не найден. Версия в `package.json` по-прежнему `1.3.0`. **Это локальный Preview, а не промышленная SaaS-платформа.**

## Зачем нужна миграция

В R2.4 Docker Compose называл тома по имени папки с распакованным клиентским приложением. При переходе на R2.5/R2.6/R2.7 применяется постоянное имя проекта Compose (`osmanx_<12 символов UUID>`). Если старые данные не перенести, новый стек может создать пустой том, и CRM покажет пустую базу.

R2.7 добавляет **host-side `deploy/volume-migrate.mjs`**, который проверяет оба комплекта и фактические Docker volume labels, заранее создаёт закрытый снимок всех существующих исходных томов и переносит данные в новые тома. Исходные тома никогда не удаляются. Автоматически запуска клиентского приложения, получения сертификатов и обновления схем БД нет.

## Требования перед запуском

- **Linux VPS** с Docker Engine и Compose. Node.js 22.16+ на хосте для скрипта.
- Текущий **распакованный** старый комплект R2.4 (формат `deploy/manifest.json` v1) и **распакованный** комплект R2.7 (формат v2). Домен, UUID проекта, тип продукта и версия движка должны совпадать.
- Остановка **обоих** Compose-стеков и всех контейнеров, использующих старые данные; старые тома должны оставаться существующими. **Никогда не используйте `docker compose down -v` или `docker volume prune` при этом переходе.**
- Достаточно места на VPS для полноценной закрытой копии томов, включая SQLite и Caddy TLS. Нужны права на Docker; не предоставляйте эти права посторонним.
- Уточнённое **историческое** имя проекта Compose: в R2.4 оно зависело от папки и могло изменяться через `-p` / `COMPOSE_PROJECT_NAME`. Возьмите значение с фактических томов Docker: `docker volume inspect ИМЯ_ТОМА`, поле `Labels["com.docker.compose.project"]`. Мигратор не угадывает его.
- Предварительно проверьте свободное место и сделайте внешнюю шифрованную копию базы. Комплект может обрабатывать до 100 000 файлов и 128 ГиБ на том; при превышении отказывает.

## Действия оператора

В приведённом примере файлы нового комплекта находятся в `/srv/osmanx/customer-new`, старого — в `/srv/osmanx/customer-r24`, а имя старого Compose-проекта — `myoldcrm`.

```bash
# Выполнить на Linux-хосте со свежим Docker Engine и доступным образом node:22
# Загрузка выполняется явно и отдельно — сам мигратор сеть не использует.
docker pull node:22-bookworm-slim

cd /srv/osmanx/customer-new
node deploy/verify.mjs
node deploy/volume-migrate.mjs plan \
  --legacy=/srv/osmanx/customer-r24 \
  --legacy-project=myoldcrm
```

Изучите имена томов, отсутствие уже существующих целевых томов и убедитесь, что приложение остановлено. Только после этого:

```bash
node deploy/volume-migrate.mjs migrate \
  --legacy=/srv/osmanx/customer-r24 \
  --legacy-project=myoldcrm \
  --confirm --offline-confirmed
node deploy/volume-migrate.mjs status
```

При завершении выводится `phase: completed`. Затем **вручную** проверьте новый `deploy/preflight.mjs`, конфигурацию Compose, запустите новый стек и убедитесь, что **те же клиентские записи** доступны и HTTP-проверка проходит. Последняя команда `node deploy/verify-live.mjs --live` проверяет настоящий внешний HTTPS и сертификат только после отдельного запуска; мигратор её не вызывает.

### Восстановление после прерывания

Если `status` показывает `recovery-required`, **не запускайте новый стек** и не удаляйте старые тома. Просмотрите `active.json` в закрытом каталоге `.osmanx-volume-migration` и снимки в `.osmanx-volume-migration/snapshots`. После выяснения причины:

```bash
node deploy/volume-migrate.mjs recover --confirm --recreate-targets
```

Команда сначала сверяет контрольные суммы закрытых резервных копий, метки ID миграции и отсутствие **любых** контейнеров, даже остановленных, связанных с целевыми томами. Она вправе удалить только целевые тома, которые **сама ранее создала**, затем восстановить их из проверенного снимка. При несоответствии меток или наличии контейнеров отказывает. Не запускайте её после начала реального использования новых томов. Если сбой произошёл до создания полных снимков, автоматическое восстановление не выполняется — нужна ручная диагностика. **Старые тома не удаляются ни при каком сценарии.**

### Защита данных и границы гарантии

- Утилита работает с остановленными томами и проверяет SHA-256 содержимого, владельца, права и тип файлов; символические ссылки и специальные файлы запрещены.
- Для `app_data` обязательно наличие `crm.sqlite` или `site.sqlite`. Локальный helper выполняет `PRAGMA integrity_check` и `PRAGMA foreign_key_check`. Он не вызывает сторонние SQL-миграции.
- Снимки создаются на хосте в директориях режима 0700 и **содержат персональные данные**. Их необходимо зашифровать и копировать в отдельное защищённое хранилище. Каталог исключён из Docker build-context.
- SHA-256 проверяет внутреннюю целостность, но **не доказывает, откуда архив пришёл**. Не устанавливайте неподтверждённые клиентские сборки.
- Внутренний копирующий контейнер работает с `--network none`, `--pull never`, неизменяемой файловой системой и минимальными файловыми полномочиями. Зависит от уже локально скачанного `node:22-bookworm-slim`.
- Автоматическое преобразование схемы базы, защищённое хранение ключей в KMS, испытанная публикация на VPS, внешняя шифрованная копия и полный облачный мониторинг **не реализованы**.

## Результаты локальной инженерной проверки

- Node.js: **54/54** автоматических теста (7 новых); прежняя регрессия и новые тесты R2.7, включая правдоподобную имитацию именованных Docker-томов, прерывание копирования, отказ по чужим Docker labels, возвращение к проверенным снимкам, реальный локальный TLS-обмен и негативные сценарии.
- Автономные приложения: **6/6** успешно распакованы и запущены на Node.js с HTTP 200 (5 CRM и сайт).
- Настоящие R2.4 ZIP для ресторанной CRM и корпоративного сайта: планирование v1 → v2 **прошло**, включая сверку UUID, домена и внутренних манифестов; сами Docker-тома не переносились.
- Настоящие ZIP R2.6 для ресторана и сайта: план совместимого обновления 0→1 к R2.7 прошёл без изменения данных.
- Chromium: обе ширины 1440 и 390 пикселей для прежнего OBSIDIAN-мастера с имитированным API; браузерный E2E с живым сервером здесь не подтверждён.
- Для полноты данных по успешным тестам см. выход `npm test`. Итоговый архив проходит повторную проверку после распаковки.

**Не проверено на настоящем VPS:** команда `docker run` для миграции, реальный Docker volume backup/restore, Caddy TLS в интернете, данные и производительность при большом объёме, регулярный мониторинг, независимый аудит безопасности. Пользоваться промышленными данными без тестовой репетиции нельзя.

## Ключевые файлы

- `templates/deploy/volume-migrate.mjs` — рабочий код мигратора.
- `src/studio/deployment.mjs` — встраивает мигратор в клиентский deployment ZIP.
- `tests/r27_volume_migration.test.mjs` — проверка миграции, отказов и восстановления.
- `tests/r27_local_tls.test.mjs` — подлинный TLS-handshake на локальном HTTPS-сервере с временным тестовым сертификатом (OpenSSL).
- `scripts/build_r27_samples.mjs` — шесть экспортируемых автономных приложений, без персональных данных.

Официальные сведения по именам/меткам томов: https://docs.docker.com/reference/compose-file/volumes/ и https://docs.docker.com/engine/storage/volumes/.
