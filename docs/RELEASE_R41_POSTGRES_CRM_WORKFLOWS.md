# R4.1 PostgreSQL CRM workflow Preview — изоляция и конкурентные изменения

## Область реализации

Это **синтетическая Preview-версия**, а не переключение производственной CRM. Оригинальная SQLite остаётся рабочей; PostgreSQL включается только с явным `OX_R40_PG_PREVIEW=YES`, локальным адресом, подписанным Ed25519 экспортом и закреплённым публичным ключом. Используется только тестовая база `ox_test_factory_r40`.

### Четыре функциональных блока

1. **Задачи:** `GET/POST/PATCH` PostgreSQL-задач, связи с неархивированными клиентами и активными сотрудниками по таблицам импортированного проекта. У `PATCH` обязателен `expectedUpdatedAt`; SQL использует сравнение старой версии в `WHERE`, чтобы две конкурентные записи не перезаписывали друг друга.
2. **Визиты:** `GET/POST`, а также атомарный `POST /visits/batch` до 10 записей. Если в середине пакета встречается несуществующий или чужой клиент, транзакция целиком откатывается.
3. **Права:** владелец использует `ox_studio` и маршрут `/api/studio/pg-preview/projects/:uuid/(tasks|visits)`; сотрудники используют сессию `ox_crm` через `/workspace/:uuid/api/pg-preview/(tasks|visits)`. `admin/manager` управляет задачами и видит визиты, `staff` видит только свои задачи (`assigned_to`) и собственные визиты (`created_by`); staff вправе менять только `status` назначенной задачи на `doing`/`done`. Все проверки сессии, роли, проекта, включённых модулей выполняются **до** обращения к PostgreSQL. ACL PostgreSQL дополнительно защищает изоляцию данных.
4. **Проверки и восстановление:** отдельная матрица GitHub Actions PostgreSQL 15/16; реальные две синтетические организации, signed import/ACL, сессии разных ролей, отказанные связи, конкурентные PATCH, атомарный откат и чтение данных после перезапуска HTTP-фабрики. Тест запрещает удалённый DB endpoint и требует пустую базу `ox_test_factory_r40` с явным подтверждением `--confirm-synthetic`.

### Безопасность

- Никаких файлов с паролями, DB URL, токенами сессий или пользовательскими CSV в Git.
- PostgreSQL writer не получает полномочий суперпользователя или создания схем. Runtime role с `NOINHERIT`; роль конкретного проекта выбирается только внутри отдельной транзакции.
- Данные клиентов в тестах синтетические. Изоляция пользователя в API ограничивается Studio-сессией владельца и локальной CRM-сессией сотрудника; это **не** самостоятельная система PostgreSQL-пользователей.
- Статус Preview и примеры запуска не означают разрешения на production cutover. Платежи и публичный HTTPS не переключены.
- Распределённых транзакций между SQLite и PostgreSQL нет. Нельзя использовать этот Preview как источник актуальных производственных данных: PostgreSQL отражает только подписанный исходный снимок и собственные Preview-изменения.

### Запуск локальных тестов

```bash
npm run test:r41
npm test
npm run check
```

В реальной CI GitHub при отдельном, пустом PostgreSQL 15/16:

```bash
npm run pg:e2e:r41
```

Команда запускается только в CI или в разрешённом оператором полностью синтетическом окружении: `PGHOST=127.0.0.1`, `PGDATABASE=ox_test_factory_r40`, `PGUSER=postgres`, `OX_R40_EPHEMERAL=YES`; перед запуском предоставляются пароль и порт отдельной тестовой БД. В рабочую БД этот тест не направлять.

### Граница готовности

После успешной реальной CI результаты подтверждают только синтетическую PostgreSQL-ветку и соответствующий HTTP API. Полная CRM (платежи, автоматизации, настраиваемые сущности, пользовательские интерфейсы) продолжает работать на SQLite и пока не перенесена. Не выдавать PG Preview за промышленный backend всей фабрики.
