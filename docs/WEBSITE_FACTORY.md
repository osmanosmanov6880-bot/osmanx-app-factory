# OSMANX APP FACTORY R0.5 — генератор корпоративных сайтов

## Что реализовано

В Factory доступны две независимо экспортируемые категории:

1. **Restaurant CRM** (R0.4): авторизация, клиенты, задачи, ручной журнал платежей, аналитика, Data Studio, внутренние страницы, версионирование и контролируемое обновление только совместимых CRM R0.4.
2. **Корпоративный сайт** (R0.5): публичный SSR-сайт, три стартовые страницы («Главная», «Услуги», «Контакты»), визуальный структурированный редактор, защищённая CMS, формы заявок, журнал обращений, базовое SEO, офлайн-резервирование SQLite, независимый экспорт исходников.

**Не реализованы:** произвольный pixel-perfect drag-and-drop, загрузка изображений, исходящие письма или WhatsApp, шаблоны стоматологий/автосервисов, интеграция с эквайрингом, Shopify/магазин, облачный хостинг, публичный деплой, автоматическая доставка обновлений для standalone-сайтов, изменения данных без авторизации, совместимость старых CRM с новым R0.5 движком.

## Создать сайт через интерфейс

1. `node server.mjs` в папке фабрики → http://127.0.0.1:4173.
2. Зарегистрировать владельца фабрики.
3. В карточке нового проекта выбрать **Корпоративный сайт** → **Универсальная компания**. Модули `auth` и `cms` обязательны, `leads` можно отключить. Цвет, подпись и контактный email настраиваются в форме.
4. Создать проект, нажать **Редактор страниц**. Изменить заголовки, секции, кнопки, преимущества. Сохранить и опубликовать.
5. Нажать **Открыть сайт**. Для управления CMS нажать **Панель CMS**. При первом запуске сайта внутри фабрики необходимо, чтобы владелец оставался авторизованным в Studio: веб-админка получает CSRF-подтверждение владельца.
6. Опубликовать неизменяемую версию через **Релизы** и скачать соответствующий ZIP или экспортировать текущую конфигурацию через **Экспорт ZIP**.

**Важно о двух редакторах.** Studio редактирует *исходную конфигурацию* и выпускаемые версии. Отдельная CMS редактирует содержимое конкретной работающей установки. Локальная правка CMS получает приоритет над последующими правками Studio этой страницы, чтобы не терять живые изменения. При экспорте Studio создаёт новый сайт из снимка Studio: содержимое локальной CMS и заявки **не входят** в архив. Страницы, удалённые в Studio, удаляются из предпросмотра установки, если они не редактировались локально. Главная страница защищена от удаления.

## Запуск экспортированного сайта

Распаковать ZIP в отдельную папку, **Node.js 22.16+**, без `npm install`:

```bash
node run.mjs
```

- http://127.0.0.1:4181/ — сайт.
- http://127.0.0.1:4181/services — услуги.
- http://127.0.0.1:4181/contacts — контактная форма (если включён модуль `leads`).
- http://127.0.0.1:4181/admin — CMS, создание первого администратора, вход, страницы, заявки, статусы, настройки.

По умолчанию сервер слушает только `127.0.0.1`. Для публичной публикации недостаточно переключить HOST: необходим обратный прокси с HTTPS, настройка домена, секрет установки, cookie `Secure`, правила хранения персональных данных, мониторинг, защита формы от спама и резервные копии вне сервера.

Переменные окружения задаются *в ОС*, файл `.env.example` только пример (проект самостоятельно `.env` не загружает):

```powershell
$env:PORT="4181"
$env:HOST="127.0.0.1"
node run.mjs
```

Перед первичной установкой на публичном сервере: `SETUP_TOKEN` (секрет от 20 символов), `COOKIE_SECURE=1` и HTTPS-прокси; на машине разработчика это не требуется. Приложение запрещает незавершённую публичную установку без ключа. `PUBLIC_SITE_URL=https://example.com` активирует sitemap.xml, robots.txt, canonical/og:url. Пока URL не установлен, сайт содержит noindex и robots запрещает сканирование, чтобы тестовая версия не индексировалась.

## Контентные блоки

Сервер принимает только строгие типы, а не произвольный пользовательский HTML/JS:

| Блок | Поля |
| --- | --- |
| `hero` | eyebrow, title, subtitle |
| `text` | title, body |
| `features` | title, 1–6 карточек title/body |
| `button` | label, внутренний `/path` либо URL `https://...`, style |
| `form` | title, submitLabel; видна только при включённом `leads` |
| `divider` | нет |

До 30 блоков и 30 страниц на сайт. Изменения сохраняются как JSON после валидации; текст выводится HTML-экранированным. Черновики недоступны посетителям. Публикация с проверкой revision, конфликт → HTTP 409.

## API сайта

Публичные маршруты:

- `GET /`, `GET /services`, `GET /contacts` — серверный HTML только опубликованных страниц.
- `GET /assets/site.css`, `/assets/site.js`, `/assets/theme.css` — стили, JS и токен акцента.
- `GET /api/health` — диагностика состояния.
- `POST /api/site/leads` — публичная JSON-форма (`name`, `phone` и/или `email`, `message`, `page`, пустое honeypot `website`); проверяется наличие опубликованной формы на странице. Базовый лимит 8 обращений/минуту на адрес источника в пределах процесса, не защита корпоративного уровня.
- `GET /robots.txt`, `GET /sitemap.xml` — правила индексации и карта страниц.

Маршруты администратора, защищённые cookie, ролью `admin`, Origin и CSRF для изменений:

- `GET /api/site/session`;
- `POST /api/site/setup`, `POST /api/site/login`, `POST /api/site/logout`;
- `GET /api/site/overview`;
- `GET /api/site/leads?limit=30&offset=0`;
- `PATCH /api/site/leads/:id` (`status: new | in_progress | closed`);
- `GET /api/site/pages`, `POST /api/site/pages`, `PATCH /api/site/pages/:id`, `DELETE /api/site/pages/:id`;
- `GET /api/site/settings`, `PATCH /api/site/settings`.

Данные каждого независимого сайта хранятся в `data/site.sqlite` и не зависят от фабрики. Во время предпросмотра в Factory у сайта своя база `data/projects/<UUID>.sqlite`, отдельная от баз других сайтов и CRM.

## Офлайн-резервные копии сайта

Остановить `node run.mjs` перед операцией:

```bash
node ops.mjs backup
node ops.mjs verify BACKUP_ID
node ops.mjs restore BACKUP_ID --confirm
```

Backup сохраняет SQLite-снимок через `node:sqlite.backup`, проверяет `PRAGMA integrity_check`, `foreign_key_check`, SHA-256. Restore требует подтверждения, заранее сохраняет отдельный recovery point. Команды не запускаются при работающем сервере. Backups сохраняют **персональные данные клиентов** — ограничивайте доступ, шифруйте внешнее хранилище и периодически проверяйте восстановление. Эти команды **не устанавливают новые релизы сайтов**: доставка обновлений и миграции CMS являются отдельной задачей.

## Папки и контракт экспорта

```text
blueprints/company-site.json
src/site/model.mjs       Валидация страниц и безопасный SSR-рендер
src/site/schema.sql      users, sessions, pages, leads, site_settings
src/site/db.mjs          Инициализация БД и источник Studio → локальный сайт
src/site/routes.mjs      Публичный HTTP и защищённая CMS
src/site/backup.mjs      Офлайн backup/verify/restore
public/site/             Готовые страницы, стили, административная панель
public/studio/editor.js  Общий редактор CRM + сайтов
src/studio/routes.mjs    Выбор шаблона и проекты с изоляцией по владельцу
src/studio/export.mjs    Автономный ZIP с конфигурацией и checksummed manifest
scripts/build_site_sample.mjs   Демосайт без клиентских записей
```

SHA-256 в `manifest.json` обеспечивает обнаружение случайной порчи, **не подписывает происхождение ZIP**. Экспорт R0.5 сайтов не совместим с `ops.mjs update` для CRM R0.4. Не выдавайте хеширование за криптографическую подпись издателя.

## Проверка релиза

- `npm run check` — синтаксис Node/браузерного JS.
- `npm test` — настоящие HTTP, SQLite, ZIP, CMS авторизация, формы, XSS, миграция Studio с R0.4, резервирование и восстановление сайта, плюс регрессии CRM.
- `python tests/ui_website_static.py` — Chromium, интерфейс сайта и CMS на 1440/390 px с тестовыми API-ответами.
- `python tests/ui_factory_site_static.py` — Chromium, выбор сайта, редактор, сохранение, мобильная компоновка с тестовыми API-ответами.

**Честная граница тестирования:** настоящие Node HTTP E2E и браузерные сценарии с замоканным API проверялись раздельно. Полный Chromium → живой localhost недоступен в среде выполнения (`ERR_BLOCKED_BY_ADMINISTRATOR`). Скриншоты находятся в `qa/site_*.png` и являются изображениями реального интерфейса с тестовым контентом, но не доказательством браузерного E2E к серверу.
