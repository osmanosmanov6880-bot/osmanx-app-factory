# OSMANX APP FACTORY — R3.2 Engineering Preview

**Дата:** 05.11.2026. **Источник:** R3.1 Preview с продолжением линии R1.3. **Тема:** безопасная смена издателя, проверяемое восстановление, диагностика перед публикацией, CI-приёмка.

Это четыре больших реализованных блока **настоящего кода**, а не изображение. Одобренный тёмный дизайн OBSIDIAN не изменён. Текущая версия `package.json` остаётся `1.3.0`: исходного кода самостоятельной ветки R2.3 у нас нет, поэтому миграция истории её версий не заявляется.

## 1. Ротация и отзыв Ed25519-ключей

**Код:** `templates/deploy/trust-policy.mjs`, интеграция с `templates/deploy/upgrade.mjs`.

До R3.2 сервер принимал только один закреплённый PEM. Теперь администратор может перейти на закрытый каталог `.osmanx-trust/keys/` с политикой `release-keyring.json`: до 8 идентификаторов, активные и отозванные ключи, отказ при несовпадении SHA-256 fingerprint, небезопасных правах или символических ссылках. Запросы обновления выбирают только тот доверенный ключ, fingerprint которого заявлен в подписанном релизе. Отозванный ключ нельзя включить обратно через `add`. Последний активный ключ отозвать нельзя. Временный переход с одним старым ключом сохранён, но невозможно заменить его чужим при инициализации без совпадения fingerprint. `--trust-key` не обходит действующую политику.

Административные команды на VPS (только после независимой проверки публичного PEM):

```bash
node deploy/trust-policy.mjs status
node deploy/trust-policy.mjs init --key=/secure/old-publisher-public.pem --confirm
node deploy/trust-policy.mjs add --key=/secure/new-publisher-public.pem --confirm
node deploy/trust-policy.mjs revoke --fingerprint=PASTE_64_HEX_FINGERPRINT --confirm
```

Важные ограничения: это **локальная политика администратора VPS**, а не автоматическая смена ключа по неаутентифицированному сообщению или из ZIP. Файлы доверия в релиз **не входят**. Никогда не предоставляйте файлы закрытого ключа. Переход на новый ключ должен происходить поэтапно: добавить публичный ключ, подписать новый пакет, обновить стенд, подтвердить приемлемую работу, только после этого отзывать старый. После отзыва нельзя устанавливать ранее подписанные старым ключом обновления; нужна новая подпись или ручная процедура восстановления доверия.

## 2. Репетиция восстановления SQLite — `drill`

**Код:** `templates/deploy/maintenance.mjs`.

Команда `drill BACKUP_ID` пользуется общим проверенным механизмом, который применяет реальное `restore`: она извлекает резервную копию SQLite в отдельную временную директорию с правами 0700, сверяет SHA-256, выполняет `PRAGMA integrity_check` и `foreign_key_check`, открывает БД только на чтение и удаляет временные данные. **Не заменяет рабочий файл SQLite**. Есть отказ при чужом проекте, подменённой копии и признаках работающего сервера. Команда не возвращает записи клиентов, только технические метаданные.

```bash
docker compose stop gateway app
docker compose --profile maintenance run --rm --no-deps maintenance backup
docker compose --profile maintenance run --rm --no-deps maintenance drill BACKUP_ID
docker compose up -d app gateway
```

`drill` — локальная проверка возвращаемости данных, не проверка внешней зашифрованной копии. Для производства отдельно испытайте восстановление на независимом сервере и резервирование WAL/SQLite при авариях.

## 3. `deploy/doctor.mjs`: единая диагностическая приёмка

**Код:** `templates/deploy/doctor.mjs`, дополнение в визуальном мастере OBSIDIAN.

По умолчанию работает без доступа к интернету и без запуска Docker. Проверяет:

- все хеши файлов, manifest/deploy identity и запрет символических ссылок в управляемых путях;
- проверяемую Ed25519-подпись с привязкой к локальной политике доверия;
- настройки домена/порта/HTTPS cookie и закрытые права `.env`, без вывода токена;
- закрытую папку резервирования и отсутствие незавершённого обновления;
- **только явно по запросу** — синтаксис Docker Compose (`--docker`) и настоящую проверку публичного TLS и identity (`--live`).

```bash
node deploy/doctor.mjs
node deploy/doctor.mjs --out=/private/r32-acceptance.json
node deploy/doctor.mjs --docker --live
```

Отчёт JSON содержит результаты, timestamp, UUID проекта, номер версии, контрольную сумму отчёта, явно отмеченный флаг `productionCertification:false`. SHA-256 отчёта не является электронной подписью. Даже все успешные проверки не дают гарантию промышленной безопасности, доступности 24/7 и работы с реальными клиентами.

## 4. Приёмка релиза и GitHub Actions

**Код:** `scripts/r32_offline_acceptance.mjs`, `scripts/build_r32_samples.mjs`, `scripts/verify_r32_samples.mjs`, `.github/workflows/r32-release-acceptance.yml`.

Интеграционная команда создаёт полностью синтетический проект, генерирует только временную тестовую пару Ed25519, выпускает ZIP, подписывает его, на локальной машине закрепляет публичный ключ, создаёт SQLite, делает реальную резервную копию, выполняет disposable `drill` и формирует отчёт `doctor`. После проверки удаляет рабочую папку. Реальных клиентских секретов, доменов или данных не использует.

```bash
npm run check
npm test
npm run acceptance:r32
node scripts/build_r32_samples.mjs /tmp/r32-samples
node scripts/verify_r32_samples.mjs /tmp/r32-samples
python3 tests/ui_r32_deploy_static.py
```

В GitHub Actions добавлен workflow с двумя этапами: `offline-acceptance` и `docker-acceptance`. Docker-часть запускается на отдельном GitHub-hosted runner и использует прежние изолированные сценарии миграции томов и подписанного обновления с откатом. В текущей среде Docker Engine не установлен, поэтому **CI workflow не был выполнен удалённо**, и его успешность пока неизвестна. Перед реальным деплоем нужно увидеть зелёный run, проверить его логи и повторить испытание на отдельном стенде.

## Что проверено локально

- `npm run check` и `npm test` — полный набор тестов (включая все предыдущие) успешно пройден.
- `npm run acceptance:r32` — подписанный ZIP + backup + disposable restore + doctor: успешно.
- 6 автономных клиентских ZIP — локальный запуск Node.js `/api/health`, корректная release identity, HTTP 200.
- Chromium на 1440 и 390 px — настоящий код интерфейса с **тестовым API**, без горизонтального переполнения.
- Исходники + patch overlay R3.1→R3.2 сверены побайтово при подготовке выпуска.

## Что НЕ проверено

Настоящий Docker Engine, VPS/SSH, сеть реального клиента, публичный TLS, real-world throughput, восстановление из off-server copy, мобильный E2E с живым сервером, аудит безопасности и совместимость с недоступной самостоятельной веткой R2.3. Подготовленные workflow не равны успешно выполненным GitHub Actions.

**Непосредственный следующий шаг R3.3:** выполнить Docker workflow на настоящем runner, исправить обнаруженные ошибки и отдельно замерить нулевую потерю записей при повторном открытии внешнего шлюза.
