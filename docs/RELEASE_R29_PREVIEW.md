# OSMANX APP FACTORY R2.9 Preview — контроль стабильности выпуска

Дата: 2026-11-05. **Инженерный Preview, не публичная промышленная SaaS-платформа.**

## Происхождение и ограничения версии

Это продолжение локальной ветки **R1.3 → R2.4 Preview → … → R2.9 Preview**. Исходный архив независимого R2.3 отсутствовал при подготовке предыдущих выпусков; совместимость с ним не подтверждена. Версия в `package.json` намеренно остаётся `1.3.0`. Название «R2.9» обозначает этап разработки, а не подтверждённый официальный semantic version.

## Реализовано в коде

1. `templates/deploy/rollout-observe.mjs` — новый независимый наблюдатель состояния уже запущенной CRM/сайта. Он проверяет через Docker **конкретный** Compose-проект, состояние контейнера `app`, статус Docker healthcheck и `RestartCount`, а также запускает существующий локальный `deploy/healthcheck.mjs`. Проверки строго ограничены по времени и числу проб. Не обращается к реальным клиентским записям, не отправляет HTTP-запросы в Интернет и не открывает порты.
2. В `templates/deploy/upgrade.mjs` после успешного старта включён **stability gate**: три последовательные проверки через 3 секунды. **Во время проверки внешний шлюз Caddy остановлен;** он запускается только после успешной проверки. Это исключает приём новых запросов через штатный шлюз перед возможным откатом (другие самостоятельно настроенные маршруты не контролируются). Если сервис нестабилен **до открытия шлюза**, применяется откат к предыдущим коду и SQLite; шлюз открывается только после восстановления. **Если открытие шлюза началось, но процесс оборвался**, автоматический откат запрещён: сначала закрывается ingress (если возможно), затем требуется ручной разбор, чтобы не стереть уже принятые клиентские записи. Факт наблюдения фиксируется в журнале обновления.
3. В закрытой `.osmanx-rollout/` создаётся краткий отчёт (без ключей, контактов, содержимого запросов и пользовательских данных). Права каталога `0700`, файлов `0600` на Unix. В `history` доступны последние 10 записей. В `*.zip`, `.gitignore`, `.dockerignore` локальные отчёты не включаются.
4. В мастер экспорта добавлен проверяемый по SHA-256 модуль `deploy/rollout-observe.mjs`. Оригинальный манифест приложения сохраняет совместимость; список файлов публикации хранится отдельно в `deploy/manifest.json`.
5. Добавлен `scripts/r29_docker_e2e.mjs` — **дополнительный** тест на настоящий Linux Docker Engine. Он требует подтверждения и уже загруженного `node:22-bookworm-slim`, создаёт случайный новый Compose-проект без опубликованных портов, запускает синтетическую CRM, подтверждает стабильное состояние, останавливает контейнер и проверяет отказ. Он не проверяет полный промышленный rollback, публичный HTTPS или Caddy. Добавлен workflow GitHub Actions для последующего запуска; **в данной среде он не запускался**.

Не применять прямо к клиентским данным без стенда и независимой резервной копии.

## Работа администратора VPS

Сначала убедитесь, что пакет сохранённой версии принадлежит конкретному проекту и что есть **проверенная резервная копия**. Не используйте инструмент для чужих ZIP и не публикуйте секреты.

```bash
node deploy/verify.mjs
node deploy/upgrade.mjs plan /private/next.zip
node deploy/upgrade.mjs apply /private/next.zip --confirm
node deploy/upgrade.mjs status
```

После успешного обновления локальный контроль повторно можно выполнить по команде:

```bash
node deploy/rollout-observe.mjs observe --samples=3 --interval-ms=3000
node deploy/rollout-observe.mjs history
node deploy/verify-live.mjs --live
```

`observe` — локальная проверка контейнера, **не** доказательство публичной доступности сайта. `verify-live` отдельно проверяет удалённое HTTPS через публичный A-запись/TLS и не заменяет бизнес-функциональную приёмку. Если обновление прервано **до открытия шлюза**, восстановление возможно по командам ниже. При фазе `manual-review-required` команда `recover` откажет и потребует ручного анализа данных:

```bash
node deploy/upgrade.mjs status
node deploy/upgrade.mjs recover --confirm
```

Проверьте данные, роли и доступность сайта до возврата клиентов. Временное падение между проверками или спустя час после обновления не обнаруживается; для промышленного SaaS нужны постоянно работающие наблюдение, алерты, логи, трассировка и процессы реагирования.

## Тест с настоящим Docker на отдельном Linux-стенде (не выполнен здесь)

```bash
docker pull node:22-bookworm-slim
npm run docker:e2e:r29
npm run docker:e2e
```

Скрипты требуют отдельного подтверждения через package scripts и используют только синтетические данные. Скрипт R2.9 создаёт временные ресурсы и проверяет их метки при очистке. Перед запуском на стенде нужно изучить исходный код и удостовериться, что Docker daemon принадлежит тестовому окружению. Не выполнять на production-хосте.
